## 1. 项目概述

### 1.1 产品目标

开发一款供朋友聚会时使用的单机猜词游戏。游戏过程中，手机横屏显示一个词语，持手机的人不能看屏幕，由朋友通过语言或动作进行提示。持手机的人根据猜测结果翻转手机：

-   **向下翻转：** 答对，得 1 分。
-   **向上翻转：** 答错 / 跳过，不得分。
-   **回到初始持机姿态：** 自动显示下一题。

游戏在限定时间内尽可能多地猜词，结束后展示成绩和本轮词语记录。

### 1.2 产品定位与边界

这是一个个人使用、朋友线下参与的轻量游戏，不需要账号体系、联网对战、排行榜或云端服务。

**本项目明确不做：**

-   不开发后端服务、API 服务或数据库服务器。
-   不做用户注册、登录和账号系统。
-   不做多人在线联机、实时同步或云端排行榜。
-   不上架 Apple App Store，不使用 TestFlight。
-   不购买 Apple Developer Program 会员。
-   第一版不开发原生 Swift / SwiftUI 客户端。

### 1.3 核心使用场景

1.  用户打开 iPhone 主屏幕上的游戏图标。
2.  选择本局的主题（如日常、歌曲、历史）和游戏时长。
3.  点击开始，按提示授权设备姿态传感器。
4.  手机横屏，屏幕显示一个大号词语。
5.  朋友向持机者描述词语，持机者进行猜测。
6.  持机者向下翻转表示答对，向上翻转表示答错 / 跳过。
7.  手机回到初始姿态后自动切换下一题。
8.  倒计时结束，展示本轮得分和答题记录。

## 2. 技术方案结论

### 2.1 推荐方案

采用 **React + TypeScript + Vite + PWA**。

将应用构建为静态网页，通过 HTTPS 部署到静态托管平台，再由 iPhone / iPad
的 Safari 添加到主屏幕。使用 Service Worker
缓存游戏所需的页面、词库、图标和音效，实现首次加载后离线运行。

### 2.2 技术选型

| 模块 | 技术 | 用途 |
| --- | --- | --- |
| 语言 | TypeScript | 业务逻辑与类型约束 |
| UI 框架 | React | 页面和组件 |
| 构建工具 | Vite | 本地开发和生产构建 |
| PWA | vite-plugin-pwa | Web App Manifest、Service Worker、离线缓存 |
| 样式 | CSS / CSS Modules | 横屏舞台、动画和适配 |
| 设备传感器 | DeviceOrientationEvent | 主数据源，用 beta / gamma 计算屏幕倾角 |
| 备用传感器 | DeviceMotionEvent | 备用数据源，用重力加速度计算屏幕倾角 |
| 屏幕常亮 | Screen Wake Lock API | 游戏中防止自动锁屏（附降级方案，见 4.8） |
| 音效 | Web Audio API | 低延迟播放；第一版可用振荡器合成，不需要音频素材 |
| 本地配置 | localStorage | 保存时长、音效、词库选择、灵敏度、已出词记录 |
| 词库 | 随代码打包的 JSON | 通过 `import` 进入构建产物，不走运行时 `fetch` |
| 单元测试 | Vitest | 测试姿态识别、洗牌、游戏状态等纯逻辑 |
| 部署 | GitHub Pages + GitHub Actions | 免费 HTTPS 静态托管，推送后自动构建发布 |

第一版不需要 Tailwind、Dexie、FastAPI、Redis、PostgreSQL
或任何后端组件，也不需要状态管理库（`useReducer` 足够）。

### 2.3 为什么选择 PWA

  对比项                      PWA                        SwiftUI 原生 App + 免费签名
  --------------------------- -------------------------- -----------------------------
  开发成本                    低                         相对较高
  是否需要 Apple 开发者会员   不需要                     不需要，但免费签名有期限
  安装方式                    Safari 添加到主屏幕        Xcode 安装
  7 天签名过期问题            没有                       有
  离线运行                    支持，需配置缓存           支持
  姿态传感器                  支持，但需授权并实机验证   原生支持更完整
  强制横屏                    iOS Safari 支持有限        原生支持
  App Store 上架              不需要                     不需要

**选择 PWA 的原因：**
本游戏主要使用屏幕显示、倒计时、本地词库、音效和姿态传感器，不依赖复杂系统
API。PWA 足以覆盖第一版需求，并避免原生 App 的签名维护成本。

### 2.4 费用与限制

-   Apple Developer Program：不需要购买。
-   App Store 上架费用：无。
-   后端服务器：无。
-   数据库：无。
-   GitHub Pages：免费。免费账号要求仓库公开，因此代码和词库对外可见；本项目不含密钥和隐私数据。
-   域名：直接使用 `https://wardell-stephen-curryii.github.io/xiaohai-guess/`，不必购买域名。

因此，第一版可以做到 **基础使用成本为 0
元**。如果未来增加付费域名、云端服务或第三方 API，则另行评估。

## 3. 功能需求

### 3.1 首页

首页包含：

-   游戏名称和简单说明。
-   **主题选择**（必选项，开始游戏前必须选定一个主题，见 3.2）。
-   游戏时长选择：30 秒、60 秒、90 秒、120 秒。
-   音效开关。
-   开始游戏按钮。
-   灵敏度设置（低 / 中 / 高，对应不同触发角度）。
-   传感器调试页入口（不显眼，用于排查问题和调参）。
-   提示文案：「请关闭静音模式并调高音量」（音效是持机者唯一的反馈渠道，见 4.7）。

默认配置建议：

-   默认主题：上一次选择的主题；第一次使用时为「混合」。
-   默认时长：60 秒。
-   默认音效：开启。
-   默认操作：向下答对、向上答错 / 跳过。

### 3.2 主题与词库

每局开始前选择一个**主题**，本局只从该主题的词库出题。一个主题对应一个词库文件（文档和代码中「主题」与「类别」指同一个东西）。

第一版内置以下主题，后续可以继续扩展：

| 主题 | 示例词 |
| --- | --- |
| 日常 | 牙刷、雨伞、外卖、挤地铁 |
| 歌曲 | 青花瓷、孤勇者、月亮代表我的心 |
| 历史 | 秦始皇、赤壁之战、四大发明 |
| 动物 | 大熊猫、长颈鹿 |
| 食物 | 火锅、煎饼果子 |
| 电影 / 电视剧 | 泰坦尼克号、甄嬛传 |
| 人物 / 名人 | 姚明、李白 |
| 成语 | 画蛇添足、对牛弹琴 |
| 体育运动 | 跳水、乒乓球 |
| 地点 | 长城、迪士尼 |
| 游戏 / 动漫 | 王者荣耀、海贼王 |
| 网络热词 | 躺平、绝绝子 |

另有一个**「混合」**选项，从所有主题中随机出题。

选择方式：

-   首页以卡片网格展示所有主题，点一下选中（单选）。
-   每张卡片显示主题名称和词条数量。
-   选中的主题记入 `localStorage`，下次打开默认选中。
-   主题的显示顺序和是否显示，由词库文件的元数据决定，增删主题不需要改界面代码。

词库随代码一起打包，每个类别一个 JSON 文件，放在 `src/data/words/`
下，通过 `import` 引入。这样不需要运行时请求、不需要加载状态，也自动进入离线缓存。

建议数据结构（每个类别一个文件）：

``` json
{
  "id": "animals",
  "name": "动物",
  "order": 4,
  "words": ["大熊猫", "长颈鹿", "袋鼠"]
}
```

说明：

-   **词条不设人工维护的 ID**，词语文本本身就是唯一键。v1.0 中
    `animal-001` 这类 ID 需要手工维护，扩充词库时容易出错，且没有实际用途。
-   用一个单元测试做词库体检：同类别内无重复、无空串、无首尾空格、长度在限制内。

词库内容要求：

-   每个类别第一版至少 80 个词，目标 150 个以上。一局 60 秒大约消耗 10--20
    个词，词太少的话玩两三局就会重复。
-   词长建议 2--7 个字。过长的词在横屏大字号下放不下，也难以描述。
-   词语难度适中：在场的人大概率都知道。
-   「网络热词」「人物 / 名人」时效性强，需要定期更新。

出题规则：

-   游戏开始时，取所选主题的词条（「混合」则合并所有主题）并随机洗牌。
-   同一局内不重复出题。
-   **跨局去重：** 把已经出过的词记录到
    `localStorage`。新的一局优先从没出过的词里抽；某个类别全部出完后，清空该类别的记录重新开始。v1.0
    只保证单局内不重复，但聚会时通常连续玩很多局，跨局重复才是真正影响体验的问题。
-   空词库或可用词条不足时，首页给出明确提示。
-   扩充词库只需要修改 JSON，不需要修改游戏逻辑。
-   词语字号根据字数自适应，保证最长的词也能在一行内完整显示。

### 3.3 游戏界面

游戏界面采用横屏布局（实现方式见 5.4），核心元素包括：

-   当前词语：屏幕中央，尽可能大的字号。
-   倒计时：角落固定显示。
-   当前得分：角落固定显示。
-   暂停按钮。
-   备用的「答对」「跳过」按钮（见 4.9）。

游戏中不显示多余信息，确保朋友在两三米外也能快速看清词语。操作提示（向下答对、向上跳过）只在开局倒计时阶段显示，游戏进行中不占用画面。

**动作反馈：** 识别到动作后，整个屏幕切换为纯色反馈画面，直到手机回正：

-   答对：绿色背景 + 「答对」大字 + 答对音效。
-   跳过：橙色背景 + 「跳过」大字 + 跳过音效。

反馈画面是给围观的朋友看的，音效是给持机者听的（持机者看不到屏幕）。

### 3.4 操作规则

| 用户动作 | 游戏行为 | 分数 |
| --- | --- | --- |
| 屏幕向下翻转并达到识别阈值 | 记录答对，显示反馈画面，播放音效 | +1 |
| 屏幕向上翻转并达到识别阈值 | 记录跳过，显示反馈画面，播放音效 | +0 |
| 回到竖直姿态 | 显示下一题，允许下一次动作识别 | 不变 |
| 时间结束 | 停止识别，进入结算 | 不变 |
| 手动暂停 / 切到后台 | 暂停倒计时和动作识别 | 不变 |

补充规则：

-   答对和跳过都只触发一次。一次翻转动作不能重复计分或连续跳过多题。
-   **等待回正期间倒计时继续走**，不暂停。
-   **时间到时屏幕上正在显示的那个词**记为「未完成」，既不算答对也不算跳过，在结算页单独显示。
-   时间到时如果正处于反馈画面（已经判定过），直接进入结算。
-   暂停后继续游戏时，重新走一遍「就绪检测 → 3-2-1」流程，因为按暂停时手机已经离开了游戏姿态。

### 3.5 结算页面

展示：

-   本轮得分（即答对数量）。
-   跳过数量。
-   正确率。
-   答对词语列表。
-   跳过词语列表。
-   未完成的词（时间到时还在屏幕上的那一个，如果有）。
-   再玩一局按钮（沿用当前设置直接开始）。
-   返回首页按钮。

正确率计算：

`正确率 = 答对数量 /（答对数量 + 跳过数量）`

当本轮没有完成任何题目时，正确率显示为「--」，避免除以 0。

结算页同时支持横屏和竖屏显示，因为这时手机通常已经拿在手里看了。

### 3.6 音效

持机者看不到屏幕，iOS 网页又不支持振动（`navigator.vibrate` 在 iOS
上不可用），**所以音效是持机者确认「动作已被识别」的唯一途径**，重要性高于 v1.0
中的定位。

需要的音效：

-   答对音效（上扬的短音）。
-   跳过音效（下沉的短音），必须和答对音效有明显区别。
-   开局 3-2-1 提示音。
-   时间到提示音。
-   最后 5 秒的滴答提示音。

实现要求：

-   使用 Web Audio API 播放，延迟低。
-   第一版用振荡器直接合成这几个短音，不需要寻找音频素材，也没有版权问题。后续想换成更好听的音效文件时，只需要替换音频模块的内部实现。
-   `AudioContext` 必须在用户点击「开始游戏」的事件处理函数中创建或恢复，否则会被 iOS 的自动播放策略拦截。
-   **静音开关：** iPhone 侧边的静音开关可能让网页声音完全无声。首页需要给出提示。能否通过
    `navigator.audioSession.type = 'playback'` 绕过静音开关，放在阶段 1 实机验证。
-   音效允许关闭。关闭后只剩画面反馈，首页要说明这一点。

## 4. 核心技术：手机姿态识别

### 4.1 技术目标

通过 iPhone / iPad 内置的陀螺仪和加速度计，判断用户是否完成翻转动作：

-   屏幕翻向地面：答对。
-   屏幕翻向天空：答错 / 跳过。

这是整个项目最重要的技术验证点。**必须先在真实 iPhone
上验证，再开发游戏主体。** 桌面浏览器和模拟器不能替代真实设备测试。

### 4.2 核心量：屏幕倾角 tilt

**不要直接对 `beta` 或 `gamma` 设阈值。** 这是对 v1.0 最重要的一处修订，原因如下：

-   `beta` / `gamma` 是欧拉角。游戏的标准姿态是「横屏竖立」，此时 `gamma`
    接近 ±90°，恰好是这套欧拉角的奇异点（万向节锁）。
-   在奇异点附近，`gamma` 到达 90° 后会折返，`beta` 会突然跳变 180°。手机只是平滑地翻了一下，读数却会剧烈跳动。
-   所以 v1.0 设想的「找出变化最明显的轴，对它设阈值」在这个姿态下不可靠，校准也救不回来。

**改用重力方向来判断。** 我们真正关心的只有一件事：屏幕朝天还是朝地。这可以由
`beta` 和 `gamma` 直接算出来，而且计算结果在奇异点处是连续的：

``` text
upZ  = cos(beta) × cos(gamma)        （角度需先换算为弧度）
tilt = asin(upZ)                     （换算回角度，范围 -90° ~ +90°）
```

| tilt | 含义 |
| --- | --- |
| +90° | 屏幕正对天空 |
| 0° | 屏幕竖直（游戏的标准姿态） |
| -90° | 屏幕正对地面 |

这个量有三个好处：

1.  **与横屏方向无关。** 无论 Home 条在左还是在右、左手还是右手持机，屏幕朝地永远是负值。
2.  **与 `alpha` 无关。** 不受指南针方向和起始参考方向影响。
3.  **物理含义固定。** 「朝地 = 答对、朝天 = 跳过」不需要用户校准轴向和正负方向。

同样可以算出另外两个分量，用于判断手机当前是哪种握持方式：

``` text
upX = -cos(beta) × sin(gamma)        （接近 ±1：横屏；正负号区分左横屏和右横屏）
upY =  sin(beta)                     （接近 ±1：竖屏）
```

**备用数据源：** 如果 `deviceorientation` 没有数据，改用 `devicemotion` 的
`accelerationIncludingGravity`，用 `z / |g|` 得到同一个量。注意两点：iOS 和 Android
上这个值的正负号相反，需要实测确定；它包含手部运动的加速度，需要更强的低通滤波。

> 以上公式由 W3C Device Orientation 规范的旋转定义推导得出，**尚未在实机上验证**。阶段 1
> 的第一件事就是在真实 iPhone 上确认这三个分量的数值和符号符合上表。

### 4.3 权限要求

iOS 对设备运动和方向数据有权限控制。实现要求：

1.  用户点击「开始游戏」时请求权限。`requestPermission()`
    必须在点击事件处理函数中**直接调用**，前面不能有 `await` 其他异步操作，否则 iOS 不认为这是用户手势。
2.  `DeviceOrientationEvent.requestPermission` 和 `DeviceMotionEvent.requestPermission`
    存在则调用，不存在则说明浏览器不需要显式授权，直接监听。
3.  **授权不是一次性的。** iOS 通常在每次重新启动 Web App 后都要再次授权，所以每次点击「开始游戏」都要走一遍请求，不能把「已授权」存进
    `localStorage` 然后跳过。
4.  **拒绝之后很难恢复。** 用户点了「不允许」后，再次调用不会重新弹窗。需要一个说明页面，告诉用户如何恢复（完全关闭
    Web App 后重新打开，或清除网站数据），同时提供屏幕按钮继续游戏。
5.  授权成功后，检查是否在 1 秒内收到有效的 `beta` / `gamma`
    数据。收不到则尝试 `devicemotion`，再收不到则进入按钮模式。
6.  传感器访问需要 HTTPS。GitHub Pages 默认提供 HTTPS；开发阶段的 HTTPS 方案见 8.1。

### 4.4 校准：取消三步校准，改为就绪检测

v1.0 设计了「记录初始姿态 → 做一次向下 → 做一次向上」的三步校准。采用 tilt
之后，轴向和方向都是物理确定的，这套校准不再需要。取消它可以省掉一个页面、一组持久化参数和一类用户操作错误。

取而代之的是每局开始前的**就绪检测**：

1.  用户点击「开始游戏」后，屏幕提示「把手机横过来举起，屏幕朝向朋友」。
2.  程序等待手机进入标准姿态：`|tilt| < 25°`，并且 `|upX| > 0.7`（确实是横屏），持续约 0.5 秒。
3.  条件满足后开始 3-2-1 倒计时，每秒一声提示音。
4.  倒计时结束，显示第一个词，开始计时。

说明：

-   **不要求放在额头上。** 举在眼前、贴在额头、举过头顶都可以，只要手机是横屏、大致竖直。
-   **传感器分辨不出屏幕朝向谁。** 程序只能判断「横屏且竖直」，无法判断屏幕是背对还是正对持机者。「屏幕朝向朋友」只能靠提示文案引导，持机者自己不偷看。
-   3-2-1 倒计时画面不显示词语，所以举起手机的过程中即使看到屏幕也不会泄题。

这样既保证了开局时手机处于中立姿态，也解决了「点完开始到举好手机这段时间算不算游戏时间」的问题。

第一版使用**绝对阈值**（以 tilt = 0° 为中立），不记录每个人的基准姿态。用户可调的只有首页的灵敏度（低 / 中 / 高）。如果实机测试发现有人习惯把手机明显前倾或后仰，再考虑在
3-2-1 期间自动采集基准值做补偿。

### 4.5 识别算法

第一版采用简单、可解释的阈值算法，不引入机器学习模型。

处理流程：

1.  每收到一个姿态事件，计算 tilt。
2.  做指数平滑。**按时间而不是按样本数平滑**（时间常数约 80ms），因为不同设备的事件频率不同。
3.  处于「中立」状态时：
    -   tilt 低于 `-触发角度` 并持续「保持时间」→ 发出 `correct` 事件；
    -   tilt 高于 `+触发角度` 并持续「保持时间」→ 发出 `skip` 事件。
4.  发出事件后进入「等待回正」状态，期间不识别任何动作。
5.  `|tilt|` 小于「回正角度」并持续「回正保持时间」→ 发出 `ready` 事件，回到「中立」状态。
6.  超过 1 秒没有收到任何姿态事件 → 发出 `sensor-lost` 事件，界面突出显示备用按钮。

初始参数（阶段 1 实测后调整）：

| 参数 | 初始值 | 说明 |
| --- | --- | --- |
| 触发角度 | 55°（灵敏度低 / 中 / 高对应 65° / 55° / 45°） | 屏幕明显朝地或朝天才算 |
| 保持时间 | 150ms | 过滤瞬时抖动 |
| 回正角度 | 25° | 与触发角度之间形成迟滞区 |
| 回正保持时间 | 200ms | 确认已经稳定回到竖直姿态 |
| 平滑时间常数 | 80ms | 降低传感器噪声 |

**实现约束：** 识别器写成不依赖 React、不依赖浏览器 API 的纯逻辑模块。输入是
`(时间戳, beta, gamma)` 序列，输出是事件。这样可以把实机录制的数据存成文件，在单元测试里回放，调参时不必每次都拿着手机翻。

**性能约束：** 姿态事件频率约 60Hz，不要把每个样本都写进 React
状态。识别器在 React 之外运行，只把 `correct` / `skip` / `ready` 这类离散事件交给界面。

### 4.6 状态设计

v1.0 把页面流转、游戏流程和动作识别画在了同一个状态机里。建议拆成三层，每层只关心自己的事：

**第一层：应用阶段**（`useReducer` 管理）

``` text
home ──点击开始──> permission ──授权完成或降级──> ready（等待横屏举好）
                                                   │
                                                   v
                                              countdown（3-2-1）
                                                   │
                                                   v
                paused <──暂停 / 切后台──────── playing ──时间到──> result
                   │                                                  │
                   └──继续──> ready                    再玩一局──> ready
                                                       返回首页──> home
```

**第二层：`playing` 内部的出题状态**

``` text
showing_word ──correct / skip──> feedback ──ready──> showing_word（下一题）
```

**第三层：姿态识别器内部状态**（见 4.5）

``` text
neutral ──达到触发条件──> wait_return ──回正并稳定──> neutral
```

关键规则：

-   只有第二层处于 `showing_word` 时，`correct` / `skip` 事件才生效。
-   每个词只产生一条答题记录。
-   **计时使用截止时间戳**（`performance.now()`
    加剩余时长），每帧计算剩余时间，不用 `setInterval`
    每秒减一。后者在页面卡顿或进入后台时会走慢。
-   暂停时保存剩余时长，继续时重新计算截止时间戳。
-   监听 `visibilitychange`，页面进入后台时自动暂停。
-   离开 `playing` 阶段时停止传感器监听、释放屏幕常亮锁。

### 4.7 反馈渠道

| 对象 | 能看到屏幕吗 | 反馈方式 |
| --- | --- | --- |
| 持机者 | 不能 | 音效（唯一渠道，iOS 网页不支持振动） |
| 围观的朋友 | 能 | 全屏绿色 / 橙色反馈画面 |

因此：音效关闭或手机静音时，持机者无法确认动作是否被识别，只能靠朋友口头告知。这一点要在首页明确提示。

### 4.8 屏幕常亮

**这是 v1.0 遗漏的一个必须项。** iPhone 默认 30 秒无触摸就自动变暗并锁屏，而一局游戏有
60--120 秒完全不碰屏幕，翻转手机并不会重置这个计时。不处理的话，游戏玩到一半屏幕就黑了。

处理方式：

1.  进入 `ready` 阶段时调用 `navigator.wakeLock.request('screen')`。
2.  页面从后台回到前台后，锁会被系统释放，需要重新申请。
3.  离开游戏阶段时主动释放。
4.  **目标设备的预期：** Wake Lock 从 iOS Safari 16.4 开始支持；在「添加到主屏幕」的
    Web App 模式下，较早的 iOS 版本存在申请成功但不生效的问题（印象中在 iOS 18.4
    前后修复）。目标设备是 iOS 26.5.1，预期可以直接使用，但仍要在阶段 1 实测确认。
5.  **降级方案（仅在实测不生效时才实现）：** 循环播放一段极小的静音视频来保持屏幕常亮；再不行则在首页提示用户临时把「设置
    → 显示与亮度 → 自动锁定」调长。

阶段 1 必须在目标 iPhone 上、以主屏幕 Web App 的方式实测这一项。

### 4.9 屏幕按钮兜底

即使传感器识别正常，也保留两个备用按钮：

-   `答对`：等价于屏幕向下翻转。
-   `跳过`：等价于屏幕向上翻转。

传感器权限被拒绝、没有有效数据或用户不方便翻转手机时，游戏仍然可以继续。在按钮模式下，点击按钮后直接显示下一题，不需要等待回正。

### 5.4 横屏适配

iOS 网页无法锁定屏幕方向：`screen.orientation.lock()` 不可用，Manifest 里的
`orientation` 字段也会被忽略。

v1.0 的方案是「竖屏时显示请横屏的提示层」。这个方案有一个严重问题：**很多人的 iPhone
常年开着竖排方向锁定**。这种情况下，手机横过来页面也不会跟着转，提示层永远不会消失，游戏玩不了。

改用**横屏舞台**方案，游戏页不依赖系统是否旋转页面：

-   游戏内容放在一个「舞台」容器里，舞台始终按横屏比例排版。
-   如果浏览器视口本身已经是横屏（用户没开方向锁定，系统已经旋转了页面）：舞台直接铺满。
-   如果视口仍是竖屏（用户开了方向锁定）：用 CSS 把舞台旋转 90° 后铺满屏幕。旋转方向根据就绪检测时的
    `upX` 正负号决定，保证文字对围观的人来说是正的。
-   两种情况下，围观者看到的画面完全一致。
-   一局游戏开始后，舞台方向固定，不在游戏中途重新判断，避免翻转手机时画面来回跳。

首页和结算页不使用舞台，按普通响应式页面处理，横竖屏都能正常显示。

iPad 使用同一套方案。

### 6.1 数据存储原则

第一版不需要数据库。所有词库、音效和图标随前端项目一起构建。

-   Safari 里打开的网页和「添加到主屏幕」后的 Web App 使用各自独立的存储，设置不互通，属于正常现象。

### 6.2 隐私

-   不采集用户身份信息。
-   不上传游戏记录。
-   不需要登录。
-   不需要分析 SDK。
-   传感器数据只在本机内存中处理，不上传服务器。

**实机调试方式（重要）：**

传感器 API 只在 HTTPS 下可用，而 `npm run dev` 默认是 HTTP，iPhone
无法直接用它测试传感器。可选方案：

| 方案 | 做法 | 特点 |
| --- | --- | --- |
| 隧道（推荐用于开发） | `npm run tunnel`（即 `cloudflared tunnel --url http://localhost:5188`） | 得到一个临时 HTTPS 地址，支持热更新，手机不需要和电脑在同一网络。需要在 Vite 的 `server.allowedHosts` 中放行隧道域名 |

| 直接部署 | 推送到 GitHub，由 Actions 发布到 GitHub Pages | 最接近正式环境，适合验证 PWA 安装和离线；每次修改都要等待重新发布 |

Safari「开发」菜单里可以打开网页检查器，查看 iPhone 上页面的 `console.log`、报错和网络请求。iPhone
访问的仍然是 Linux 开发机通过隧道提供的地址，Mac 只用来查看。需要先在 iPhone 的「设置 → App →
Safari → 高级」中打开「网页检查器」。

调试页仍然需要以下两项，因为翻转测试时屏幕背对着自己，不方便同时看 Mac：

-   把 tilt、识别状态和识别计数直接显示在屏幕上。
-   提供「录制 → 导出」功能，把一段姿态数据复制到剪贴板或下载为文件，用于调参和单元测试回放。

GitHub Pages 的项目站点部署在 `/xiaohai-guess/` 子路径下，不是域名根目录。因此：

-   `vite.config.ts` 中设置 `base: '/xiaohai-guess/'`。
-   Manifest 的 `start_url` 和 `scope` 使用相对路径 `./`；图标路径不以 `/` 开头。
-   `index.html` 中的图标等资源同样不能写成以 `/` 开头的绝对路径。
-   代码中引用静态资源时使用 `import.meta.env.BASE_URL`，不写死路径。
-   本应用只有一个页面，不使用前端路由，因此不存在刷新子页面出现 404 的问题。

上面 8.2 的示例配置中，图标路径在实现时需要按这里的要求去掉开头的 `/`。

**其他说明：**

-   提交到公开仓库的 git 提交记录会带上提交者邮箱。本仓库单独配置提交邮箱为
    `linxingwang627@163.com`，不使用本机全局配置里的工作邮箱。
-   **网络可达性：** `github.io` 在中国大陆的部分网络下访问不稳定。目标手机已实测可以打开。应用只有首次加载和版本更新时需要联网；如果以后出现打不开的情况，
    备选方案是 Cloudflare Pages（目标手机已实测可以打开 `pages.dev`）。

### 8.5 安装到 iPhone / iPad

1.  在 iPhone / iPad 上使用 Safari 打开部署地址。
2.  点击 Safari 的分享按钮。
3.  选择「添加到主屏幕」。
4.  如果出现「作为 Web App 打开」选项，将其开启。
5.  点击「添加」。
6.  返回主屏幕，点击新生成的游戏图标启动。

安装后是主屏幕 Web App，不是通过 App Store 安装的原生 IPA。

### 8.6 离线运行验证

首次访问和安装需要网络。完成首次加载、Service Worker
激活并确认静态资源缓存后，再进行离线测试：

1.  正常联网打开应用。
2.  等待首页、词库、音效和图标全部加载。
3.  关闭应用，再重新从主屏幕图标打开。
4.  开启飞行模式。
5.  再次打开应用，检查首页和游戏能否正常运行。
6.  测试开始游戏、翻转识别、倒计时、音效和结算。

注意：离线能力依赖 Service Worker
缓存成功。系统清理网站数据、用户手动删除 Web App
或缓存被清除后，可能需要重新联网加载。

## 9. 测试计划

### 9.1 第一优先级：真实设备姿态识别验证

先开发一个最小传感器测试页面，只显示：

-   当前 `beta` / `gamma` 值。
-   计算出的 tilt、upX、upY。
-   当前识别状态。
-   当前识别结果。
-   权限状态。

测试步骤：

1.  使用真实 iPhone 的 Safari 打开 HTTPS 测试页面。
2.  点击按钮申请传感器权限。
3.  **验证 tilt 公式：** 屏幕朝天平放应为约 +90°，横屏竖立应为约 0°，屏幕朝地应为约 -90°。
4.  **验证 `upX`：** 横屏竖立时接近 ±1，两种横屏方向符号相反。
5.  横屏举起、屏幕背对自己，缓慢向下翻转再回正，确认 tilt 连续变化、没有跳变。向上同理。
6.  分别测试左手、右手持机和两种横屏方向，确认结果一致。
7.  用正常游戏的速度连续做 20 次动作，统计漏判和误判次数。
8.  正常拿稳、说话、轻微晃动、走动，确认不会误触发。
9.  录制几段数据并导出，用于调参和单元测试。
10. **竖排方向锁定：** 分别在开启和关闭锁定的情况下测试横屏舞台显示是否正确。
11. **屏幕常亮：** 不触摸屏幕放置 2 分钟，确认屏幕不变暗、不锁屏。在 Safari
    和主屏幕 Web App 两种方式下分别测试。
12. **音效：** 确认答对 / 跳过音效能播放；打开静音开关后再测一次，记录是否有声音。
13. **权限：** 测试点「不允许」之后的表现，以及关闭 Web App 重新打开后是否需要再次授权。

把结果记录到 `docs/实机测试记录.md` 中（设备型号、iOS 版本、每项结果）。

**以上全部通过，或者对不通过的项确定了降级方案之后，再进入游戏主体开发。**

## 10. 风险与应对

| 风险 | 影响 | 应对方式 |
| --- | --- | --- |
| 游戏中屏幕自动变暗 / 锁屏 | 游戏中断 | Wake Lock；不生效时用静音视频降级；阶段 1 实机验证（见 4.8） |
| 横屏竖立姿态处于欧拉角奇异点 | 读数跳变，识别错乱 | 不直接使用 beta / gamma，改用 tilt（见 4.2） |
| 用户开启竖排方向锁定 | 页面不旋转 | 横屏舞台，用 CSS 自行旋转（见 5.4） |
| iOS 传感器权限被拒绝 | 无法翻转识别 | 屏幕按钮兜底，并说明如何恢复授权 |
| 手机处于静音模式 | 持机者得不到任何反馈 | 首页提示；验证能否绕过静音开关 |
| 手持抖动导致误判 | 误计分 | 按时间平滑、保持时间、迟滞区、状态锁 |
| 翻转测试时无法同时查看调试信息 | 调参困难 | 调试页屏显关键数值，支持录制导出；报错用 Mac 的网页检查器查看 |
| `github.io` 在当地网络不可达 | 无法首次加载和更新 | 正式部署前实测；备选 Cloudflare Pages（已确认可访问） |
| 页面进入后台后计时不准确 | 游戏时间异常 | 截止时间戳计时；监听 `visibilitychange` 并暂停 |
| 音效被自动播放策略拦截 | 没有声音 | 在点击「开始游戏」的处理函数中初始化音频 |
| 词库太小 | 玩几局就重复 | 每类至少 80 词；跨局去重 |
| 缓存未完成 | 离线无法启动 | 首页显示「已可离线使用」状态；执行断网验收 |
| iOS 清理网站数据 | 本地缓存和设置丢失 | 保持资源轻量，重新联网加载即可恢复 |

### 10.1 关于横屏的特别说明

iOS 网页无法锁定屏幕方向，也不能假设用户关闭了竖排方向锁定。游戏页使用横屏舞台自行处理方向，详见 5.4。

### 10.2 关于离线的特别说明

PWA 并不意味着第一次打开就能无网络运行。需要先通过 HTTPS 加载应用，并让
Service Worker 成功缓存所有必要资源。完成后才可离线使用。

## 13. 给 Codex / Claude Code 的实施要求

建议将本文档作为项目的开发依据，并按里程碑逐步实现。

开发约束：

1.  **先做传感器 PoC，不要先做完整 UI。** 第一阶段必须在真实 iPhone
    上验证。
2.  不要引入后端、数据库、登录、云同步或在线排行榜。
3.  不要为了架构完整而过度设计，第一版保持简单。
4.  姿态识别逻辑独立封装，不要写在页面组件中。
5.  游戏流程使用明确状态管理，确保一次动作只触发一次。
6.  所有游戏资源（词库、音效、图标）随前端静态构建。
7.  必须支持传感器不可用时的触屏操作。
8.  必须支持 Service Worker 离线缓存。
9.  必须在真实 iPhone 上测试，不能只用桌面模拟器验收。
10. 每完成一个阶段先运行测试并说明结果，再继续下一阶段。

**建议第一条开发任务：** 创建 Vite + React + TypeScript
项目，只实现一个调试页面。在真实 iPhone 上通过 HTTPS 打开，完成 9.1
列出的全部验证：tilt 公式、翻转识别、屏幕常亮、音效、横屏舞台。通过后再开发游戏主体。
